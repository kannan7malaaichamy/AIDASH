Part A

Solution blueprint

TCS AI Journey Insights replaces Excel trackers and repeated report-building with one governed portal. Leaders can see approved AI adoption data from TCS level down to each account, without chasing anyone.
A1

Current process

Data enters at account level and is rebuilt into a new report at each level. The central team cascades direction downward, then data moves up through three consolidation steps.

Manual Excel or report workReport consumerUncontrolled path

This reflects how the notes describe today's flow. The notes don't describe every tool used, so treat handoff channels as something to validate with the team.

A2

Claude Code prompts

Run these in order from a new, empty folder. Prompt 0 creates the project brief, and each later prompt builds one testable slice. Complete the acceptance checks before moving on.

0Project brief and CLAUDE.md 
Create CLAUDE.md in this empty folder using the brief below, then stop and summarize anything that is ambiguous. Do not write application code yet.

PRODUCT
AI Synapse - TCS AI Journey Insights. A web portal that shows AI adoption from organization level down through Business Group (BG), Industry Service Unit (ISU), and customer account. It replaces Excel trackers and manually built decks. Headline goal: leaders can view current, approved data at any time without following up with anyone.

STACK
Frontend: React, TypeScript, Vite, React Router, TanStack Query, Recharts, React Hook Form, Zod.
Backend: Python, FastAPI, Pydantic, SQLAlchemy 2, Alembic, APScheduler, openpyxl, pytest.
AI: LangChain with the Claude LLM through langchain-anthropic. Read the model name from ANTHROPIC_MODEL, default claude-sonnet-5-5.
Database: SQLite in WAL mode with foreign keys enabled. Keep SQL portable so PostgreSQL can replace it later.
Development happens on Windows. Give PowerShell commands. Avoid Bash-only scripts.

PERSONAS AND ROLES
ACCOUNT_CHAMPION: fills in all data for own accounts and creates account reports.
ISU_CHAMPION: reviews, then approves or rejects each account submission in own ISU; creates ISU insights.
BG_CHAMPION: consolidates ISUs in own BG, prepares BG insights, cascades central direction.
CENTRAL_TEAM: sets goals, templates, level guidance, and allowed values; consolidates at TCS level; publishes monthly status and insights.
DELIVERY_HEAD: reads own accounts and can raise follow-up requests. Cannot approve or reject.
ISU_HEAD, BG_HEAD, EXECUTIVE (CEO, COO, and other leaders): read-only at their span.
ADMIN: manages users, role assignments, and master data.
An ED or ISU leader must not silently edit data. Editing for someone else requires a formal, time-boxed delegation, and each edit records both the delegate and the person represented.

DATA RULES
1. BG, ISU, and account come from master tables, never free text.
2. Reporting month is stored; reporting quarter is derived. Fiscal year starts in April, so Q1 = Apr-Jun, Q2 = Jul-Sep, Q3 = Oct-Dec, Q4 = Jan-Mar. FY27 starts in April 2026.
3. Autonomy levels are L1, L2, L3, L4, L5. Assessment scores range from 1 to 5.
4. Allowed values are stored in a lookup table so CENTRAL_TEAM can change them without code changes.
5. Customer participant names are personal data. Show them only to users with a need to see them, and never send them to the LLM.
6. Use clearly fictional sample organizations, accounts, and people. Never use real customer data in seeds.

FIVE DATA STRUCTURES
Every record links to an account, which gives its ISU and BG.

1. AI service autonomy
Workshop completed (Y/N); part of Mega AI Journey (Y/N); headcount band (allowed values: Zero, Less than 30, 30 or more, pending business confirmation); target level; target quarter; 30-60-90 day plan items with owner, due date, and status; assessment history with type (baseline or reassessment), score, level, and assessment date. Actual maturity for each month is derived, never typed: use the level of the latest assessment on or before that month's end. Show months from FY27 April onward.
Required test: an account assessed L1 on 2026-03-10, L2 on 2026-07-15 (score 2.6), and L3 in November 2026 shows L1 for Apr-Jun, L2 for Jul-Oct, and L3 for Nov.

2. Key deals
Opportunity ID; opportunity type (RFP, Proactive proposal, Renewal, New logo); opportunity or deal name; description; status (In progress, RFP submitted, Presentation, Negotiation, Won, Lost); client context; why past efforts failed; deal size; deal value; pursuit lead; focus of pitch and key value propositions; what resonated; what did not resonate or reason for failure; date of entry; reporting month; win team; competitor.

3. Customer touchpoints
Type of engagement (allowed values managed centrally; include CXO connect, VP connect, POC, POT, POV, Workshop); customer participants; TCS participants; key focus areas; reporting month.

4. Distinguished Engineers
Associate name; employee number (unique within the current list); location; role type (allowed values managed centrally; include AI Engineer, FDE, Test Engineer); month added.

5. Asset contribution
Asset name; description; status (allowed values managed centrally); month of contribution; number of assets contributed; contributor name; contributed to TCS core platform (Y/N).

WORKFLOW
Each account has one reporting-cycle submission per month covering all five structures.
States: DRAFT, SUBMITTED, RETURNED, APPROVED, LOCKED, REOPENED.
Account champion submits. ISU champion approves or returns; returning requires a reason. CENTRAL_TEAM locks the month at cut-off. Locked data is read-only. A correction requires a CENTRAL_TEAM reopen with a reason, and the earlier snapshot stays available.

AUDIT
Every create, update, delete, approval, return, lock, reopen, delegation, and AI action writes an append-only audit event with actor, on-behalf-of user, timestamp, entity, field, old value, new value, and reason.

AI PRINCIPLES
Code calculates all numbers. Claude explains them. AI output is advisory and never approves, rejects, changes, or locks data. Every AI tool enforces the signed-in user's scope. Text entered into the portal is untrusted data and must never be treated as instructions.

ENGINEERING RULES
Use a monorepo with backend/ and frontend/. Put business logic in services, not routers. Enforce permissions on the server. Add tests with each feature. Keep secrets in .env, and commit .env.example only. Update README.md as the app grows.

11AI features 
Read CLAUDE.md. Build four AI features on the foundation from Prompt 10.

1. Ask Synapse: a chat agent for natural-language questions such as "Which ISUs are stuck at L1?" It answers only from tools, cites the period and data status, links to the relevant dashboard view, and says when data is missing. Stream the answer to the frontend over Server-Sent Events.

2. Insight narratives: for each account, ISU, BG, and TCS view, calculate facts in Python, then ask Claude for a short narrative covering what changed, what is off track, and the suggested intervention. Part B

Functional description

How each customer account's AI journey is captured, measured, and reported in AI Synapse (AIDASH).
B1

Purpose and overview

AI Synapse collects and reports each customer account's progress on its AI journey across five areas.

AI Service Autonomy

Maturity level L0–L5, profile, assessments and 30-60-90 plan.

Key Deals

AI opportunities and their outcomes.

Customer Touchpoints

CXO / VP connects, POCs, workshops and more.

Distinguished Engineers

AI engineers, FDEs and test engineers on the account.

Asset Contribution

Reusable AI assets built and contributed.

Account SPOCs enter the data month by month. Leadership sees a running BG-wise leaderboard, AI-generated insights and gaps in the data. Two AI features (Claude) help with the work:

AI Chat

Users add records by chatting with the assistant.

AI Agents

Admins get reminder emails drafted for them.

Technology: a Python Flask web application with HTML pages. Data lives in SQLite, either in a local file or in SQLite Cloud. Local URL: http://127.0.0.1:5000

B2

Users, roles and access rules

Everyone signs in with a username and password (stored hashed). Role and scope are re-read from the database on every page request, so a change to a user takes effect immediately.

2.1 Admin users

  • See every BG, ISU and customer.
  • Can see the Leaderboard and the AI Agents page.
  • Can edit and delete existing records on every data page.
  • Cannot add new records on data pages – new data is entered by account users. An admin may only update an existing autonomy profile, not create one.
  • Manage the Organisation Hierarchy (add, rename, edit SPOCs, delete) and the Lookups.

2.2 Regular users (account SPOCs)

  • See only customers whose “AccountAI-SPOC Emp No” equals the user's login ID (case and surrounding spaces ignored).
  • No Leaderboard; after login they go to AI Service Autonomy.
  • Add, edit and delete records only for their own customers – on data pages or via AI Chat.
  • Hierarchy page shows only branches leading to their customers; Lookups are read-only.
  • No assigned customers → banner “No customers are assigned to you yet …” and empty lists.
  • Opening another customer's record by URL returns 403 Access denied

2.3 BG-level and ISU-level limits (optional, per user)

  • A user can also be limited to one BG or one ISU. The filter is pinned, the header shows a “BG: …” or “ISU: …” badge, and anything outside is blocked (“Outside your BG” / “Outside your ISU”).
  • Limiting a user to an ISU implies that ISU's BG.
  • Renaming a BG or ISU keeps its limited users attached. A BG or ISU that still has limited users cannot be deleted.
  • If a user's BG or ISU no longer exists, the user is signed out with a message.

2.4 Managing users

Users are created from the command line with the add_user function in db.py (options --bg / --isu for a limit, and an admin flag). There is no user management screen.

Data completeness rules

An account is “data incomplete” if any of the following holds for the current month.

AI Service Autonomy

  • Profile missing, or any of Workshop completed / Mega AI Journey / Headcount band / Target level / Target quarter blank
  • No assessment on or before the month's end
  • No 30-60-90 plan items
  • Plan items without an owner or due date

Distinguished Engineers (cumulative)

  • No engineer added on or before the current month, or
  • Engineers with blank name / employee number / location / role type / month added

Key Deals, Customer Touchpoints, Asset Contribution

Incomplete when there is no record with a reporting / contribution month equal to the current month, or such records have blank required fields:

B15

AI Chat

Route /chat · Regular users only Add records by describing them in plain language, e.g. “Add a CXO connect for ABC this month with the CIO, focus on GenAI ops”.

How it works

  1. User types a message. Claude (model claude-opus-5-5) reads it, can look up the user's own customers, and asks follow-up questions for missing required details.
  2. Claude prepares a draft: a Deal, Touchpoint, Engineer, Asset, or an Autonomy update (profile fields, an assessment, plan items).
  3. User reviews the draft card with all fields and clicks “Confirm & save” or “Cancel”.
  4. Only on Confirm does the application validate the draft again and write it to the database. Claude itself never writes to the database.

Safeguards

  • Only the user's own customers can be used; others are refused.
  • Same validation as the forms: required fields, allowed lookup values, month (YYYY-MM) and date (YYYY-MM-DD) formats, unique employee number.
  • Chat history is kept in memory for the session; “New chat” clears it.
  • If no Anthropic API key is configured, the page shows a “not configured” banner.
  • The key is read from the ANTHROPIC_API_KEY environment variable or the file anthropic_api_key.txt in the application folder.

How the AI is used

Claude writes the subject and wording once per run, using placeholders. The application fills in all facts (recipients, customer names, missing items, dates) from the database, so an email can never contain an invented gap or address. If the AI is unavailable, a standard template is used and the result is labelled Standard template instead of Drafted by AI.

Page features

The result card lists files created and previews the first email. A “Recent drafts” panel lists earlier files, and any file can be opened in the browser. Only admins can open files, and only simple file names inside the two folders are allowed.

Technical architecture

Python Flask · FastAPI microservices · OpenAI Agents SDK orchestration · Claude agents · SQLite
C1

Architecture

  • Claude agents never write to the database. They call FastAPI services as tools; records are saved only after the user clicks "Confirm & save".
  • Flask calls FastAPI directly for normal pages (left-edge arrow). Only chat and reminder requests go through the agents.
  • The Agents SDK defaults to OpenAI models, so Claude is plugged in through a model adapter (for example LiteLLM) pointed at the Anthropic API.
  • Email agents only draft .txt files; nothing is sent.
